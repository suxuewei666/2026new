### 1.reactive 和 ref 的区别，为什么reactive不能定义原始值类型
区别：

reactive 用于对象（包括数组、嵌套对象），返回一个响应式代理，直接操作属性即可响应更新。
ref 用于原始值（如数字、字符串、布尔值）或对象，返回一个带 .value 属性的响应式对象，访问和修改时需用 .value。
为什么 reactive 不能定义原始值类型？

reactive 的底层实现是 Proxy，只能代理对象，不能代理原始值（如 number、string、boolean），否则会报错或无效。
原始值没有属性，无法被 Proxy 拦截和追踪变化。
如果你需要原始值响应式，必须用 ref，它会把原始值包裹在一个对象的 .value 属性里。
总结：

对象用 reactive
原始值用 ref
reactive 不能代理原始值，因为 Proxy 只能代理对象，原始值没有属性可追踪。

### 3.写一个圣杯布局，中间自适应
圣杯布局经典实现如下，中间自适应，两侧定宽：
<div class="container">
  <div class="header">header</div>
  <div class="main">
    <div class="left">left</div>
    <div class="center">center</div>
    <div class="right">right</div>
  </div>
  <div class="footer">footer</div>
</div>

.container { min-width: 600px; }
.header, .footer { height: 60px; background: #eee; }
.main {
  display: flex;
}
.left, .right {
  width: 200px;
  background: #ccc;
}
.center {
  flex: 1;
  background: #fafafa;
}
核心：main 用 display: flex，center 用 flex: 1 实现自适应，两侧定宽。圣杯布局也可用浮动实现，但现代项目推荐 flex。


### 4.组件封装思路？颗粒度考虑
组件封装思路与颗粒度考虑如下：

拆分原则

单一职责：每个组件只负责一个功能，易维护、易复用。
复用性：抽离通用部分为基础组件，如 Button、Input。
组合性：复杂组件由基础组件组合而成，如表单、列表。
颗粒度选择

过细：每个小功能都拆成组件，代码冗余，沟通成本高。
过粗：一个组件包含太多功能，难以复用和维护。
推荐：以业务场景和复用频率为依据，*UI基础组件颗粒度细，业务组件颗粒度适中*。
封装要点

明确 props、事件、插槽，保证组件可配置、可扩展。
保持 API 简洁，文档清晰。
关注样式隔离和命名空间，避免冲突。
实际流程

先设计基础组件（如按钮、输入框）。
再设计业务组件（如商品卡片、用户列表）。
组件库统一管理，便于维护和升级。
总结：
颗粒度以“复用性+维护性”为核心，基础组件细，业务组件适中，遵循单一职责和组合复用原则。
